# Архитектура Nokia Router MedveFlasher

Технический разбор для разработчиков и любопытных: как устроена установка, чем
всё передаётся, и на каких приёмах держится путь без UART. Пользователю это
читать не обязательно — для установки достаточно [инструкции](README_RU.md).

---

## Принципы

**Ноль сторонних зависимостей.** Весь ПК-мастер — на стандартной библиотеке
Python 3. Ни `requests`, ни `pyserial`, ни `cryptography`, ни браузера. Причина
не в аскетизме: целевой пользователь не разработчик, и каждая внешняя библиотека
— это команда в консоли, которую можно не так набрать, и необходимость интернета
в момент, когда компьютер уже подключён кабелем к роутеру. Поэтому написаны
собственные реализации там, где обычно берут пакет:

- **AES-128-CBC + RSA-1024** для входа в веб-интерфейс — чистый Python, сверено
  с векторами FIPS-197 и NIST SP 800-38A (`stock_web.py --selftest`);
- **Win32-бэкенд COM-порта** через `ctypes` и `kernel32` — вместо `pyserial`,
  включая правильные `COMMTIMEOUTS` для XMODEM;
- **TFTP-сервер и клиент**, **XMODEM**, разбор **FIT/DTB** — тоже свои.

**Fail closed.** На единственном устройстве со стоком любая неопределённость —
остановка, а не «попробуем». Особенно перед стиранием NAND и записью BL2.

## Разметка NAND штатной прошивки

Мастер работает с фиксированной стоковой разметкой XG-040G-MD (`FIXED_EXPECTED`
в `master.py`). Ключевые разделы:

```text
mtd0   bootloader   0x00080000   (BL2 + U-Boot + env)
mtd14  nsb_master   0x02880000   ← сюда пишется transition-образ
mtd16  all_flash    0x0EBA0000   полный образ NAND (основа backup/restore)
```

Внутри `mtd0`: BL2 в первых `0x20000`, U-Boot environment по offset `0x1C000`
внутри erase-блока `0x60000`, размер payload `0x4000`.

**Два допустимых варианта слотов.** Разделы `mtd2`..`mtd5` у стока существуют в
двух зеркальных раскладках (A/B) — какая активна, зависит от того, с какого
слота устройство загружалось последний раз. `SLOT_LAYOUTS` в `master.py`
содержит обе, и проверка разметки принимает любую из них:

```text
вариант A   mtd2=0x003AF6DA  mtd3=0x01CC0000  mtd4=0x00480000  mtd5=0x02400000
вариант B   mtd2=0x00480000  mtd3=0x02400000  mtd4=0x003AF6DA  mtd5=0x01CC0000
```

Размеры остальных разделов (`FIXED_EXPECTED`) фиксированы и сверяются точно:
несовпадение любого — остановка с `mtd{N}: размер ..., ожидается ...`.

## Полный цикл установки

```text
┌─────────────┐   Telnet    ┌──────────────┐
│     ПК      │────────────▶│  сток Nokia  │
│  master.py  │   backup    │  (штатная)   │
└─────────────┘◀────────────└──────────────┘
      │ 1. backup mtd0..mtd16 → проверка
      │ 2. env_patcher: правка bootcmd в mtd0-env
      │ 3. запись transition в mtd14 + patched env в mtd0
      ▼
┌──────────────────────────────────────────┐
│ reboot → штатный U-Boot читает mtd14,     │
│ грузит transition initramfs OpenWrt в RAM │
└──────────────────────────────────────────┘
      │ 4. initramfs сам форматирует NAND под UBI
      │    и ставит постоянный OpenWrt (sysupgrade)
      ▼
┌──────────────────────────────────────────┐
│ постоянный OpenWrt all-in-UBI с LuCI      │
└──────────────────────────────────────────┘
```

## Ноу-хау: патчинг bootcmd вместо замены загрузчика

Это ядро пути без UART. Обычная установка OpenWrt на такое железо требует
доступа к U-Boot по последовательному порту. Мы обходимся без него так:

**Шаг 1 — извлечение env из backup.** После снятия backup `env_patcher.py` берёт
из дампа `mtd0` штатный U-Boot environment (erase-блок `0x60000`, payload по
`0x1C000` размером `0x4000`). Он **сохраняет каждый байт** вне payload и **все
переменные**, меняя ровно одну — `bootcmd`:

```text
flash read 0xc0000 0x800000 0x92000000; bootm 0x92000000
```

Эта команда велит штатному U-Boot прочитать transition-образ из NAND (по
физическому offset, куда он ляжет после записи в `mtd14`) в RAM по `0x92000000`
и загрузить его как FIT. Затем `env_patcher` пересчитывает **CRC32** окружения
(иначе U-Boot отвергнет env) и выдаёт образ ровно `0x20000` байт.

**Шаг 2 — запись.** Мастер пишет transition-образ в `mtd14`, а патченный env — в
`mtd0` **последним** и с проверкой чтением обратно. Сам загрузчик U-Boot не
трогается — меняется только его команда автозапуска.

**Шаг 3 — перезагрузка.** Штатный U-Boot исполняет новый `bootcmd`, поднимает
transition OpenWrt из NAND в RAM. UART при этом не нужен — вся логика уже в env.

Почему это безопасно: env привязан к конкретному устройству (уникальные MAC,
серийники), поэтому персональный пакет нельзя перенести на другой роутер.
Загрузчик не заменён, так что при сбое устройство остаётся штатно загружаемым до
момента форматирования NAND на этапе 2.

## Ноу-хау: transition-образ со встроенным snapshot

`transition-bundle.bin` — это не просто initramfs. Внутри него FIT-образ
OpenWrt initramfs, а в него **встроен полный production sysupgrade** (SNAPSHOT
OpenWrt с LuCI). Смысл: после того как transition-система поднялась в RAM, ей не
нужно ничего скачивать — образ постоянной системы уже при ней.

Что делает transition initramfs автоматически (этап 2), без единой ручной
команды:

1. поднимает сеть и SSH;
2. проверяет плату, MTD-разметку, NAND и её геометрию;
3. проверяет встроенные BL2, FIP и sysupgrade по SHA256;
4. **форматирует NAND от `0x20000` до конца как UBI**;
5. создаёт UBI-разделы: `ubootenv`, `ubootenv2`, `bosa`, `ri`, `fip`, `fit`;
6. записывает `bosa` и `ri` (из backup), Ethernet-fixed FIP, возвратный FIT;
7. проверяет всё чтением обратно;
8. записывает полный **BL2 последним** (с preloader, offset `0x800`);
9. запускает `sysupgrade -v -n` встроенного образа (`-n` — не переносить
   временную конфигурацию).

BL2 пишется последним намеренно: до этого момента устройство восстановимо
повтором, потому что старый загрузчик ещё цел.

Точные версии встроенного образа (профиль, target, ревизия SNAPSHOT, ядро,
SHA256, offset в bundle) — в [IMAGE_STATUS_RU.md](IMAGE_STATUS_RU.md).

## Ноу-хау: ручной режим для экспертов

Помимо `transition-bundle.bin` есть `transition-manual-bundle.bin` — тот же
transition initramfs, но **без встроенного sysupgrade** и без автоматического
этапа 2. Он для тех, кто хочет поставить **свой** образ, а не тот SNAPSHOT, что
вшит в основной bundle.

Сценарий эксперта:

1. мастер пишет manual-transition в `mtd14`, роутер грузится в него;
2. вместо автоустановки мастер просит указать **свой `.itb`** на компьютере;
3. файл передаётся по TFTP в RAM роутера;
4. перед записью проверяются: FIT magic, размер, SHA256,
   `nokia-ubi-installer check` и `sysupgrade -T`;
5. форматирование NAND запускается **только после второго подтверждения**.

Так эксперт получает контроль над тем, какая именно система встанет, сохраняя те
же проверки безопасности, что и в автоматическом пути.

## Транспорты передачи

### Backup (роутер → ПК)

Образ NAND (~250 МБ) снимается на устройстве через `dd | gzip` и передаётся одним
из способов, которые пользователь выбирает по доступности служб:

| Транспорт | Как работает |
|---|---|
| **USB-флешка** | backup-агент пишет дампы прямо на смонтированную флешку в роутере; ПК почти не участвует |
| **USB + Samba** | флешка монтируется, ПК забирает готовые дампы по SMB |
| **USB + FTP** | то же по FTP (учитывается chroot-представление USB-пути) |
| **Прямой TFTP** | флешка не нужна: `dd | gzip` пишется в TFTP-поток прямо на ПК (UDP/1069 по умолчанию, порт спрашивается) |

TFTP-путь переиспользует один исправный root-сеанс Telnet и переподключается
только после сбоя.

### Установочный пакет (ПК → роутер)

Мастер собирает пакет (transition-образ, patched env, `INSTALL.sh`, агент,
`SHA256SUMS`) и доставляет его на устройство:

- **Samba/FTP** — заливкой файлов в сетевой ресурс, откуда их видит роутер;
- **прямой** — `send_file_to_router` по TFTP/nc в `/tmp`.

На устройстве `INSTALL.sh` сверяет `SHA256SUMS` и запускает preflight, затем flash.

### Восстановление стока (ПК → роутер)

При откате блоки образа передаются в порядке **TFTP → SCP → TCP/nc** (следующий
транспорт пробуется, если предыдущий недоступен). После каждого записанного
раздела — проверка чтением обратно по SHA256. SCP-приёмник в recovery-образе
ограничен: принимает только `scp -t` и только в `/tmp`.

## RAM-worker: как пережить стирание собственного rootfs

Проблема этапа 2: форматирование NAND стирает раздел, из которого работает сама
установочная система. Решение — RAM-worker: критичная часть установщика
копируется в tmpfs и запускается оттуда, так что продолжает работать, когда
исходный rootfs уже стёрт. Мастер отслеживает его по маркеру
`__NOKIA_RAM_WORKER_STARTED__` в выводе.

## Определение модели и защита от кирпича

XG-040G-MD (AN7581) и близкая XG-040G-MF (AN7583) имеют **побайтно совпадающую
стоковую разметку NAND** и одинаковый `/proc/cpuinfo` (Cortex-A53). Проверка по
`/proc/mtd` их не различает. Единственный надёжный признак — чип из
`device_status.cgi` веб-интерфейса: `AN7581` против `AN7583`.

Поэтому в автоматическом режиме (вариант **1**) мастер **до первой записи**
читает модель через веб-интерфейс (`StockSetup.require_model`) и останавливается
на MF, не откатываясь на ручной ввод — иначе проверку можно было бы обойти.
Установка образа от MD на MF привела бы к кирпичу, восстановимому только через
UART. MF без UART в принципе не берётся: там закрыт сетевой root — подробности в
истории проекта.

Гарантия неодинакова для всех вариантов подключения. Точная политика в коде
(`ask_credentials`, поле `AccessProfile.model_gate_policy`):

| Вариант | Что делает мастер с проверкой модели |
|---|---|
| **1** — автоматическая настройка | Строгий гейт через `device_status.cgi`. AN7583 → жёсткая остановка до любой записи |
| **2** — настроить Telnet вручную | `model_gate_policy = "best-effort"`: веб-морда недоступна, вместо неё UID-0 проба по Telnet. Явный AN/EN7583 отвергается, AN/EN7581 принимается, **неопределённый вывод пропускается после одного предупреждения** |
| **3** — использовать включённый Telnet | То же, что и вариант 2 |
| **4** — свой образ OpenWrt (эксперт) | Модель **не проверяется вообще**. Печатается `[ОПАСНО]`, требуется явное `y/N`. Защитой остаётся только то, что NAND не форматируется до валидации выбранного sysupgrade |

Иначе говоря: строгая проверка чипа есть только на варианте 1. Варианты 2 и 3
дают ослабленную проверку, вариант 4 — не даёт никакой и опирается на осознанное
подтверждение оператора.

## Восстановление кирпича через UART

Крайний случай, когда U-Boot уже не грузится и BootROM повторяет `C` в UART —
ждёт следующий этап загрузки по XMODEM. Последовательность:

```text
BootROM C → XMODEM preloader → RAM
         → XMODEM BL31+U-Boot FIP → RAM
U-Boot из RAM (мастер захватывает AN7581>)
         → TFTP каждого 8-МиБ блока IBU из backup
         → mtd write → mtd read → hash sha256 (поблочно)
         → BL2 последним + проверка
         → reset → загрузка стока
```

Временные компоненты (preloader, FIP) работают только из RAM и в NAND не
пишутся. Захват U-Boot строгий: после подтверждения XMODEM мастер шлёт `Ctrl-C`,
выходит из bootmenu через `ESC` и требует устойчивое приглашение `AN7581>` —
Enter не отправляется, он выбрал бы «загрузку по умолчанию».

## Обращение с секретами

Пароль веб-интерфейса не попадает в `LATEST.log`, `state.json` или командную
строку; разово передаётся через `NOKIA_WEB_PASSWORD` (мастер удаляет переменную
из окружения после чтения). Прочитанные из морды пароли Telnet/FTP держатся
только в памяти процесса. Вход шифруется AES/RSA; открытая форма — только по
`NOKIA_ALLOW_PLAIN_WEB_LOGIN=1` с предупреждением (RSA-ключ берётся по HTTP, что
не защищает от активного MITM).

**Эхо при вводе включено намеренно.** Вопреки привычному поведению, пароль по
умолчанию **виден на экране**: `_localized_getpass` вызывает обычный `input()`,
а не `getpass`. Это осознанный компромисс для неопытного пользователя, который
иначе не понимает, почему при вводе «ничего не происходит». Скрытый ввод
включается переменной `NOKIA_HIDE_PASSWORDS=1`. Эхо терминала генерируется не
Python, поэтому в файлы сессии оно не копируется.

**Фильтрация логов и её граница.** Известные секреты регистрируются через
`_register_log_secret()` и вырезаются из вывода подстановкой `[REDACTED]` в
`_ConsoleTee`. Ограничение по построению: значения **короче 4 символов не
фильтруются** — иначе глобальная подстановка уничтожила бы обычную диагностику.
Пароль Nokia с этикетки заметно длиннее, поэтому на практике фильтр работает,
но короткий пользовательский пароль в логе не будет скрыт.

## Целостность комплекта: `verify_kit()`

Перед работой мастер проверяет собственный комплект и **отказывается стартовать**
при любом расхождении. Это не формальность: проверка сцепляет Python и shell.

1. наличие всех обязательных файлов (`transition-bundle.bin`,
   `transition-manual-bundle.bin`, шаблон лаунчера, backup-агент, `stock_web.py`,
   `env_patcher.py`, recovery preloader/FIP/initramfs);
2. точный размер и SHA256 обоих transition-бандлов;
3. SHA256 всех трёх recovery-артефактов;
4. **сверку метаданных внутри `stock-launcher.sh.in` с реальным бандлом** —
   `BUNDLE_SIZE`, `BUNDLE_SHA`, `TRANSITION_TOTALSIZE`, `TRANSITION_FIT_SHA`,
   `TRANSITION_WINDOW_SHA`, `SYSUPGRADE_SIZE`, `SYSUPGRADE_SHA`.

Пункт 4 важен для тех, кто правит код: значения ищутся регуляркой
`^KEY=(.+)$` и сравниваются как строки, **включая одинарные кавычки**. Любое
переформатирование лаунчера, нормализация кавычек автоформаттером или смена
порядка строк ломает старт мастера целиком. Отдельная ловушка: сравнение делает
`.strip()`, поэтому хвостовой `\r` от CRLF **этой проверкой не ловится** — за
переводы строк отвечает `.gitattributes`, а не `verify_kit()`.

Параллельно `data/SHA256SUMS` покрывает весь поставляемый комплект и должен
регенерироваться при изменении любого входящего в него файла.

## Telnet-сессии и root-гейт

Собственная реализация Telnet (`class Telnet` в `master.py`) — не `telnetlib`,
который из стандартной библиотеки Python удалён. Политика подключения:

- до **3 независимых root-сессий**, в каждой до **3 попыток свежего TCP-логина**;
- обязательный гейт: `id -u` должен вернуть `0`, иначе сессия отвергается;
- повышение до root через `su` с подбором UID-0 учёток (`_read_uid0_accounts`,
  `_ordered_uid0_candidates`);
- все команды, уходящие на устройство, экранируются `shlex.quote()`;
  `subprocess` вызывается только списком аргументов, `shell=True` не
  используется нигде.

В TFTP-пути один исправный сеанс переиспользуется между разделами;
переподключение происходит только по тайм-ауту, ошибке сокета/Telnet или
отсутствию маркера завершения.

## Вывод, локализация и логирование

Небанальное архитектурное решение, которое стоит понимать до правки кода:
`master.py` **переопределяет `print`, `input` и `getpass.getpass` на уровне
модуля**:

```python
print = _localized_print
input = _localized_input
getpass.getpass = _localized_getpass
```

Это сделано намеренно и является fail-closed механизмом: локализацию и
подкраску **нельзя забыть**, потому что через них проходит любой вывод.
Замена на явные обёртки сделала бы механизм обходимым — забытый `print()` тихо
ушёл бы мимо локализации.

Следствия, о которые легко споткнуться:

- переопределение действует **только в глобалях `master.py`**. Вынос кода в
  отдельный модуль пакета вернёт туда builtin `print`, и локализация отвалится
  молча, без ошибки;
- `tr()` вызывает `ensure_language()`, который при незаданном языке **спрашивает
  пользователя через stdin**. То есть `tr()` — не чистая функция. Вычисление
  `tr()` на уровне модульных констант или из рабочего потока даст интерактивный
  запрос при импорте либо гонку за stdin;
- по той же причине неинтерактивный запуск требует `NOKIA_LANG`:
  `python3 data/master.py --help` без неё спросит язык до argparse и упадёт на EOF;
- английские тексты берутся из двух источников: явных `tr(ru, en)` и каталога
  подстановок `_RU_EN`, применяемого к сообщениям исключений через
  `Error.__str__`. На момент написания около **82 из 205** мест `raise` полагаются
  именно на каталог. Удалять каталог можно только после того, как все они
  переведены явно — иначе английский пропадёт ровно на аварийных путях, молча.

Весь консольный вывод дублируется в `work/logs/LATEST.log` через `_ConsoleTee`,
с вырезанием ANSI-последовательностей и подстановкой `[REDACTED]` вместо
зарегистрированных секретов.
