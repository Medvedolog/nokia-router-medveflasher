# Архитектура Nokia Router MedveFlasher

Технический разбор для разработчиков и любопытных: как устроена установка, чем
всё передаётся, и на каких приёмах держится путь без UART. Пользователю это
читать не обязательно — для установки достаточно [инструкции](INSTRUCTION_RU.md).

---

## Принципы

**Ноль сторонних зависимостей.** Весь ПК-мастер — на стандартной библиотеке
Python 3. Ни `requests`, ни `pyserial`, ни `cryptography`, ни браузера. Причина
не в аскетизме: целевой пользователь не разработчик, и каждая внешняя библиотека
— это команда в консоли, которую можно не так набрать, и необходимость интернета
в момент, когда компьютер уже подключён кабелем к роутеру. Поэтому написаны
собственные реализации там, где обычно берут пакет:

- **AES-128-CBC + RSA-1024** для входа в веб-интерфейс — чистый Python, сверено
  с векторами FIPS-197 и NIST SP 800-38A (`stock_web.py --selftest`);
- **Win32-бэкенд COM-порта** через `ctypes` и `kernel32` — вместо `pyserial`,
  включая правильные `COMMTIMEOUTS` для XMODEM;
- **TFTP-сервер и клиент**, **XMODEM**, разбор **FIT/DTB** — тоже свои.

**Fail closed.** На единственном устройстве со стоком любая неопределённость —
остановка, а не «попробуем». Особенно перед стиранием NAND и записью BL2.

## Разметка NAND штатной прошивки

Для install-path мастер сохраняет фиксированную стоковую разметку XG-040G-MD (`FIXED_EXPECTED`
в `master.py`). Ключевые разделы:

```text
mtd0   bootloader   0x00080000   (BL2 + U-Boot + env)
mtd14  nsb_master   0x02880000   ← сюда пишется transition-образ
mtd16  all_flash    0x0EBA0000   stock restore span (основа backup/restore; не вся физическая NAND)
```

Внутри `mtd0`: BL2 в первых `0x20000`, U-Boot environment по offset `0x1C000`
внутри erase-блока `0x60000`, размер payload `0x4000`.

**Два допустимых варианта слотов.** Разделы `mtd2`..`mtd5` у стока существуют в
двух зеркальных раскладках (A/B) — какая активна, зависит от того, с какого
слота устройство загружалось последний раз. `SLOT_LAYOUTS` в `master.py`
содержит обе, и проверка разметки принимает любую из них:

```text
вариант A   mtd2=0x003AF6DA  mtd3=0x01CC0000  mtd4=0x00480000  mtd5=0x02400000
вариант B   mtd2=0x00480000  mtd3=0x02400000  mtd4=0x003AF6DA  mtd5=0x01CC0000
```

Размеры остальных разделов (`FIXED_EXPECTED`) фиксированы и сверяются точно:
несовпадение любого — остановка с `mtd{N}: размер ..., ожидается ...`.

## Полный цикл установки

```text
┌─────────────┐   Telnet    ┌──────────────┐
│     ПК      │────────────▶│  сток Nokia  │
│  master.py  │   backup    │  (штатная)   │
└─────────────┘◀────────────└──────────────┘
      │ 1. backup mtd0..mtd16 → проверка
      │ 2. env_patcher: правка bootcmd в mtd0-env
      │ 3. запись transition в mtd14 + patched env в mtd0
      ▼
┌──────────────────────────────────────────┐
│ reboot → штатный U-Boot читает mtd14,     │
│ грузит transition initramfs OpenWrt в RAM │
└──────────────────────────────────────────┘
      │ 4. initramfs сам форматирует NAND под UBI
      │    и ставит постоянный OpenWrt (sysupgrade)
      ▼
┌──────────────────────────────────────────┐
│ постоянный OpenWrt all-in-UBI с LuCI      │
└──────────────────────────────────────────┘
```

## Ноу-хау: патчинг bootcmd вместо замены загрузчика

Это ядро пути без UART. Обычная установка OpenWrt на такое железо требует
доступа к U-Boot по последовательному порту. Мы обходимся без него так:

**Шаг 1 — извлечение env из backup.** После снятия backup `env_patcher.py` берёт
из дампа `mtd0` штатный U-Boot environment (erase-блок `0x60000`, payload по
`0x1C000` размером `0x4000`). Он **сохраняет каждый байт** вне payload и **все
переменные**, меняя ровно одну — `bootcmd`:

```text
flash read 0xc0000 0x800000 0x92000000; bootm 0x92000000
```

Эта команда велит штатному U-Boot прочитать transition-образ из NAND (по
физическому offset, куда он ляжет после записи в `mtd14`) в RAM по `0x92000000`
и загрузить его как FIT. Затем `env_patcher` пересчитывает **CRC32** окружения
(иначе U-Boot отвергнет env) и выдаёт образ ровно `0x20000` байт.

**Шаг 2 — запись.** Мастер пишет transition-образ в `mtd14`, а патченный env — в
`mtd0` **последним** и с проверкой чтением обратно. Сам загрузчик U-Boot не
трогается — меняется только его команда автозапуска.

**Шаг 3 — перезагрузка.** Штатный U-Boot исполняет новый `bootcmd`, поднимает
transition OpenWrt из NAND в RAM. UART при этом не нужен — вся логика уже в env.

Почему это безопасно: env привязан к конкретному устройству (уникальные MAC,
серийники), поэтому персональный пакет нельзя перенести на другой роутер.
Загрузчик не заменён, так что при сбое устройство остаётся штатно загружаемым до
момента форматирования NAND на этапе 2.

## Ноу-хау: transition-образ со встроенным snapshot

`transition-bundle.bin` — это не просто initramfs. Внутри него FIT-образ
OpenWrt initramfs, а в него **встроен полный production sysupgrade** (SNAPSHOT
OpenWrt с LuCI). Смысл: после того как transition-система поднялась в RAM, ей не
нужно ничего скачивать — образ постоянной системы уже при ней.

Что делает transition initramfs автоматически (этап 2), без единой ручной
команды:

1. поднимает сеть и SSH;
2. проверяет плату, MTD-разметку, NAND и её геометрию;
3. проверяет встроенные BL2, FIP и sysupgrade по SHA256;
4. **форматирует NAND от `0x20000` до конца как UBI**;
5. создаёт UBI-разделы: `ubootenv`, `ubootenv2`, `bosa`, `ri`, `fip`, `fit`;
6. записывает `bosa` и `ri` (из backup), Ethernet-fixed FIP, возвратный FIT;
7. проверяет всё чтением обратно;
8. записывает полный **BL2 последним** (с preloader, offset `0x800`);
9. запускает `sysupgrade -v -n` встроенного образа (`-n` — не переносить
   временную конфигурацию).

BL2 пишется последним намеренно: до этого момента устройство восстановимо
повтором, потому что старый загрузчик ещё цел.

Точные версии встроенного образа (профиль, target, ревизия SNAPSHOT, ядро,
SHA256, offset в bundle) — в [IMAGE_STATUS_RU.md](IMAGE_STATUS_RU.md).

## Ноу-хау: ручной режим для экспертов

Помимо `transition-bundle.bin` есть `transition-manual-bundle.bin` — тот же
transition initramfs, но **без встроенного sysupgrade** и без автоматического
этапа 2. Он для тех, кто хочет поставить **свой** образ, а не тот SNAPSHOT, что
вшит в основной bundle.

Сценарий эксперта:

1. мастер пишет manual-transition в `mtd14`, роутер грузится в него;
2. вместо автоустановки мастер просит указать **свой `.itb`** на компьютере;
3. файл передаётся по TFTP в RAM роутера;
4. перед записью проверяются: FIT magic, размер, SHA256,
   `nokia-ubi-installer check` и `sysupgrade -T`;
5. форматирование NAND запускается **только после второго подтверждения**.

Так эксперт получает контроль над тем, какая именно система встанет, сохраняя те
же проверки безопасности, что и в автоматическом пути.

## Транспорты передачи

### Backup (роутер → ПК)

Образ NAND (~250 МБ) снимается на устройстве через `dd | gzip` и передаётся одним
из способов, которые пользователь выбирает по доступности служб:

| Транспорт | Как работает |
|---|---|
| **USB-флешка** | backup-агент пишет дампы прямо на смонтированную флешку в роутере; ПК почти не участвует |
| **USB + Samba** | флешка монтируется, ПК забирает готовые дампы по SMB |
| **USB + FTP** | то же по FTP (учитывается chroot-представление USB-пути) |
| **Прямой TFTP** | флешка не нужна: `dd | gzip` пишется в TFTP-поток прямо на ПК (UDP/1069 по умолчанию, порт спрашивается) |

TFTP-путь переиспользует один исправный root-сеанс Telnet и переподключается
только после сбоя.

### Установочный пакет (ПК → роутер)

Мастер собирает пакет (transition-образ, patched env, `INSTALL.sh`, агент,
`SHA256SUMS`) и доставляет его на устройство:

- **Samba/FTP** — заливкой файлов в сетевой ресурс, откуда их видит роутер;
- **прямой** — `send_file_to_router` по TFTP/nc в `/tmp`.

На устройстве `INSTALL.sh` сверяет `SHA256SUMS` и запускает preflight, затем flash.

### Восстановление стока (ПК → роутер)

При откате блоки образа передаются в порядке **TFTP → SCP → TCP/nc** (следующий
транспорт пробуется, если предыдущий недоступен). После каждого записанного
раздела — проверка чтением обратно по SHA256. SCP-приёмник в recovery-образе
ограничен: принимает только `scp -t` и только в `/tmp`.

## RAM-worker: как пережить стирание собственного rootfs

Проблема этапа 2: форматирование NAND стирает раздел, из которого работает сама
установочная система. Решение — RAM-worker: критичная часть установщика
копируется в tmpfs и запускается оттуда, так что продолжает работать, когда
исходный rootfs уже стёрт. Мастер отслеживает его по маркеру
`__NOKIA_RAM_WORKER_STARTED__` в выводе.

## Определение модели и защита от кирпича

XG-040G-MD (AN7581) и близкая XG-040G-MF (AN7583) используют одну и ту же
**крупную физическую карту stock `all_flash`**: bootloader/romfile, оба NSB,
BOSA, RI, flags, config, data, oopsfs и log находятся на тех же физических
границах, а `mtd16` имеет размер `0x0EBA0000`. Однако vendor-подразделы
`mtd2..mtd5` (`kernel/rootfs` A/B) **не являются побайтным инвариантом**: их
размеры могут отличаться между MD и MF/версиями stock. Поэтому install-path не
определяет модель по `/proc/mtd`; надёжный гейт остаётся по чипу из
`device_status.cgi`: `AN7581` против `AN7583`.

Поэтому в автоматическом режиме (вариант **1**) мастер **до первой записи**
читает модель через веб-интерфейс (`StockSetup.require_model`) и останавливается
на MF, не откатываясь на ручной ввод — иначе проверку можно было бы обойти.
Установка MD-образа на MF по-прежнему запрещена. rc9 поддерживает для MF **brick recovery по UART** из собственного полного stock backup и отдельный read-only BootROM backup; обычный no-UART install остаётся MD-only.

Гарантия неодинакова для всех вариантов подключения. Точная политика в коде
(`ask_credentials`, поле `AccessProfile.model_gate_policy`):

| Вариант | Что делает мастер с проверкой модели |
|---|---|
| **1** — автоматическая настройка | Строгий гейт через `device_status.cgi`. AN7583 → жёсткая остановка до любой записи |
| **2** — настроить Telnet вручную | `model_gate_policy = "best-effort"`: веб-морда недоступна, вместо неё UID-0 проба по Telnet. Явный AN/EN7583 отвергается, AN/EN7581 принимается, **неопределённый вывод пропускается после одного предупреждения** |
| **3** — использовать включённый Telnet | То же, что и вариант 2 |

Иначе говоря: строгая Web-проверка чипа есть на варианте 1. Варианты 2 и 3 дают ослабленную Telnet-проверку. Выбор собственного sysupgrade больше не меняет политику model gate и выполняется отдельно до выбора способа подключения.

## Восстановление кирпича через UART

Крайний случай, когда U-Boot уже не грузится и BootROM повторяет `C` в UART —
ждёт следующий этап загрузки по XMODEM. Последовательность:

```text
BootROM C → XMODEM SoC-specific preloader → RAM
         → XMODEM SoC-specific BL31+U-Boot FIP → RAM
U-Boot из RAM (AN7581> / AN7583> / U-Boot> / =>)
         → TFTP каждого 8-МиБ блока IBU из backup
         → PC SHA256 pin + RAM crc32
         → mtd write → mtd read → crc32 (поблочно)
         → BL2 из выбранного backup последним + CRC32-проверка
         → reset → загрузка стока
```

Временные компоненты (preloader, FIP) работают только из RAM и в NAND не пишутся. Для MD используются проверенные AN7581/Nokia recovery-артефакты. Для MF используются release-pinned AN7583 RAM preloader/FIP, которые полный rollup возит с собой; перед BootROM они проверяются локально, без runtime download. Сам BootROM/XMODEM recovery flow аппаратно проверен; конкретная exact-byte пара может перепиниваться между snapshot-релизами и тогда требует отдельного HW re-confirmation. Реальный MF подтвердил BootROM → AN7583 preloader → BL31/U-Boot → `U-Boot>`, автоматический `mtd list`, сетевые `setenv` и TFTP первого 8-МиБ блока. Этот U-Boot не содержит `hash sha256`, поэтому rc9 проверяет RAM после TFTP и readback командой `crc32`, а исходные PC-файлы остаются закреплены SHA256. Если RAM U-Boot не захвачен, NAND не меняется.

Захват U-Boot строгий: Ctrl-C отправляется только после появления баннера/меню U-Boot, а не периодически во время всей инициализации. После первого `AN7581>`, `AN7583>`, аппаратно наблюдавшегося на MF `U-Boot>` либо стандартного `=>` мастер ждёт тишину UART, чтобы отложенные break-символы не повредили первую команду. Enter не отправляется. Команда и проверка её `$?` идут отдельными CR-строками; `; echo marker` в одной строке не используется. Перед первой записью автоматический `mtd list` обязан подтвердить `bl2=0x20000`, `ubi=0x0FFE0000` и erase block `0x20000`. В rc8fix2 эти значения и scripted command path аппаратно подтверждены на MF; также подтверждены сетевые `setenv` и TFTP первого 8-МиБ блока.

## Read-only backup через BootROM/UART

RC9 переиспользует тот же безопасный bootstrap, но после захвата RAM U-Boot **не выполняет никаких NAND write-команд**. В rc9fix после открытия UART нет операторского `input()` перед BootROM: мониторинг начинается немедленно, `Press x`/`C` ловятся автоматически, а первый RX-буфер намеренно не очищается. Очистка stale ACK/`C` применяется только перед последующей XMODEM-стадией. После точного `mtd list` модельный recovery FIT загружается по TFTP в RAM и запускается `bootm`. Recovery обязан подтвердить UID 0, ожидаемый `board_name`, `all_flash=0x10000000` и наличие `dd`, `gzip`, `tftp`, `sha256sum`.

```text
BootROM → XMODEM preloader/FIP → RAM U-Boot
        → mtd list (read-only gate)
        → TFTP recovery FIT → RAM Linux
        → dd /dev/mtd0 блоками ≤ 8 MiB
        → gzip | TFTP PUT → PC
        → повторный dd | sha256sum → сравнение с PC
        → сборка mtd16 и совместимого mtd0..mtd16 набора на ПК
```

Снимается только stock-диапазон `0x00000000..0x0EBA0000`, даже если физический NAND имеет 256 MiB. Это делает результат напрямую пригодным для существующего restore pipeline. Каждый блок имеет sidecar `.raw.sha256`; уже проверенные блоки можно переиспользовать после обрыва. `mtd2..mtd5` — перекрывающиеся vendor views внутри `mtd14/mtd15`; поскольку BootROM-съёмка не имеет штатного `/proc/mtd`, мастер нормализует их в допустимую layout A. Авторитетные raw-данные — `mtd14`, `mtd15` и канонический `mtd16`.

В backup-mode в dispatcher отсутствуют `erase/write/saveenv/sysupgrade`; recovery используется только из RAM. PC-side splitter и `verify_stock_restore_backup()` проверены на реальном MF `mtd16`; end-to-end аппаратный capture — новый путь rc9.

## Обращение с секретами

Пароль веб-интерфейса не попадает в `LATEST.log`, `state.json` или командную
строку; разово передаётся через `NOKIA_WEB_PASSWORD` (мастер удаляет переменную
из окружения после чтения). Прочитанные из морды пароли Telnet/FTP держатся
только в памяти процесса. Вход шифруется AES/RSA; открытая форма — только по
`NOKIA_ALLOW_PLAIN_WEB_LOGIN=1` с предупреждением (RSA-ключ берётся по HTTP, что
не защищает от активного MITM).

**Эхо при вводе включено намеренно.** Вопреки привычному поведению, пароль по
умолчанию **виден на экране**: `_localized_getpass` вызывает обычный `input()`,
а не `getpass`. Это осознанный компромисс для неопытного пользователя, который
иначе не понимает, почему при вводе «ничего не происходит». Скрытый ввод
включается переменной `NOKIA_HIDE_PASSWORDS=1`. Эхо терминала генерируется не
Python, поэтому в файлы сессии оно не копируется.

**Фильтрация логов и её граница.** Известные секреты регистрируются через
`_register_log_secret()` и вырезаются из вывода подстановкой `[REDACTED]` в
`_ConsoleTee`. Ограничение по построению: значения **короче 4 символов не
фильтруются** — иначе глобальная подстановка уничтожила бы обычную диагностику.
Пароль Nokia с этикетки заметно длиннее, поэтому на практике фильтр работает,
но короткий пользовательский пароль в логе не будет скрыт.

## Целостность комплекта: `verify_kit()`

Перед работой мастер проверяет собственный комплект и **отказывается стартовать**
при любом расхождении. Это не формальность: проверка сцепляет Python и shell.

1. наличие `VERSION`, `data/VERSION`, `MANIFEST.json` и всех обязательных payload/скриптов; обе версии и `MANIFEST version/build_tag` обязаны совпадать с кодом;
2. наличие MD recovery preloader/FIP/initramfs, `recovery/mf/OPENWRT_SNAPSHOT.json` и bundled MF stock-recovery FIT;
3. точный размер и SHA256 обоих transition-бандлов;
4. SHA256 трёх встроенных MD recovery-артефактов и bundled MF stock-recovery FIT, плюс exact size/SHA256 двух bundled AN7583 EVB RAM stages и точное совпадение MF snapshot provenance metadata с закреплёнными в коде именами/размерами/SHA256;
5. **сверку метаданных внутри `stock-launcher.sh.in` с реальным бандлом** —
   `BUNDLE_SIZE`, `BUNDLE_SHA`, `TRANSITION_TOTALSIZE`, `TRANSITION_FIT_SHA`,
   `TRANSITION_WINDOW_SHA`, `SYSUPGRADE_SIZE`, `SYSUPGRADE_SHA`.

Пункт 4 важен для тех, кто правит код: значения ищутся регуляркой
`^KEY=(.+)$` и сравниваются как строки, **включая одинарные кавычки**. Любое
переформатирование лаунчера, нормализация кавычек автоформаттером или смена
порядка строк ломает старт мастера целиком. Отдельная ловушка: сравнение делает
`.strip()`, поэтому хвостовой `\r` от CRLF **этой проверкой не ловится** — за
переводы строк отвечает `.gitattributes`, а не `verify_kit()`.

Параллельно `data/SHA256SUMS` покрывает весь поставляемый комплект и должен
регенерироваться при изменении любого входящего в него файла.

---

## Telnet-сессии и root-гейт

Собственная реализация Telnet (`class Telnet` в `master.py`) — не `telnetlib`,
который из стандартной библиотеки Python удалён. Политика подключения:

- до **3 независимых root-сессий**, в каждой до **3 попыток свежего TCP-логина**;
- обязательный гейт: `id -u` должен вернуть `0`, иначе сессия отвергается;
- повышение до root через `su` с подбором UID-0 учёток (`_read_uid0_accounts`,
  `_ordered_uid0_candidates`);
- все команды, уходящие на устройство, экранируются `shlex.quote()`;
  `subprocess` вызывается только списком аргументов, `shell=True` не
  используется нигде.

В TFTP-пути один исправный сеанс переиспользуется между разделами;
переподключение происходит только по тайм-ауту, ошибке сокета/Telnet или
отсутствию маркера завершения.

## Вывод, локализация и логирование

Небанальное архитектурное решение, которое стоит понимать до правки кода:
`master.py` **переопределяет `print`, `input` и `getpass.getpass` на уровне
модуля**:

```python
print = _localized_print
input = _localized_input
getpass.getpass = _localized_getpass
```

Это сделано намеренно и является fail-closed механизмом: локализацию и
подкраску **нельзя забыть**, потому что через них проходит любой вывод.
Замена на явные обёртки сделала бы механизм обходимым — забытый `print()` тихо
ушёл бы мимо локализации.

Следствия, о которые легко споткнуться:

- переопределение действует **только в глобалях `master.py`**. Вынос кода в
  отдельный модуль пакета вернёт туда builtin `print`, и локализация отвалится
  молча, без ошибки;
- `tr()` вызывает `ensure_language()`, который при незаданном языке **спрашивает
  пользователя через stdin**. То есть `tr()` — не чистая функция. Вычисление
  `tr()` на уровне модульных констант или из рабочего потока даст интерактивный
  запрос при импорте либо гонку за stdin;
- по той же причине неинтерактивный запуск требует `NOKIA_LANG`:
  `python3 data/master.py --help` без неё спросит язык до argparse и упадёт на EOF;
- английские тексты берутся из двух источников: явных `tr(ru, en)` и каталога
  подстановок `_RU_EN`, применяемого к сообщениям исключений через
  `Error.__str__`. На момент написания около **82 из 205** мест `raise` полагаются
  именно на каталог. Удалять каталог можно только после того, как все они
  переведены явно — иначе английский пропадёт ровно на аварийных путях, молча.

Весь консольный вывод дублируется в `work/logs/LATEST.log` через `_ConsoleTee`,
с вырезанием ANSI-последовательностей и подстановкой `[REDACTED]` вместо
зарегистрированных секретов.

# Приложение. Контракты и инварианты по релизам

Ниже — трассировка: в каком релизе появился тот или иной архитектурный контракт и почему. Это не пользовательская хронология изменений — она в [CHANGELOG_RU.md](CHANGELOG_RU.md). Разделы сгруппированы по релизам и строгого порядка по датам не образуют.

## 1.0.0-rc28 — автономность RAM-worker, включая его голос

**Инвариант, сказанный прямо.** `mtd3` — представление внутри `mtd14`, поэтому стирание transition-цели уносит с собой stock rootfs. После этой первой destructive операции ни один executable, library, shell helper *или logging primitive*, который worker ещё использует, не может браться со stock NAND. Замыкание команд это уже соблюдало — всё шло через размещённые BusyBox и `mtd_debug`, — а канал отчётности не соблюдал, причём сразу двумя способами.

Worker запускался с выводом в `/dev/null`, а переданные ему пути `ramlog`/`usb_log` присваивались и ни разу не использовались. Каждая строка этапа и каждое `CRITICAL FAILURE` уходили в никуда. Worker, стёрший `mtd14` и остановившийся, не оставлял записи о причине — ровно наблюдавшийся инцидент: стирание прошло, записано ничего не было, и читать потом оказалось нечего.

Хуже того, размещённый скрипт запускал `nokia_begin_output_mirror` для `--ram-flash`. Этому mirror нужны `tee` и `mkfifo`, обе резолвятся по `PATH` с того rootfs, который вот-вот сотрут. Канал, обязанный доложить о стирании, сам становился его жертвой.

**Лечение — удаление, а не починка.** Tee и FIFO — это ещё две сущности, способные умереть между стиранием и сообщением о том, почему стирание оказалось последним, что произошло. Worker теперь не поднимает mirror вообще: его stdout и stderr — обычный открытый файл в tmpfs, поэтому `rlog` это shell `printf` в уже открытый дескриптор — ни pipeline, ни вспомогательного процесса, ни внешнего `nohup`, а `trap '' HUP` перед `exec` и так переживает отвал Telnet. То, что `mtd_debug` пишет в stderr, сохраняется само собой. Лог в каталоге bundle на stock NAND удалён вместе с аргументом, который его нёс, поэтому запуск, диспетчер и worker сходятся на контракте из девяти аргументов.

## 1.0.0-rc27 — личность, состояние и авторизация в restore-пути

**Три вопроса, которые были одним.** Откат без UART задавал единственный: равен ли `board_name` точной строке с `-ubi`, которую ставит этот комплект, и совпадают ли три строки `/proc/mtd` как текст. И отвечал «не соответствует» одинаково на transition-систему этапа 1, на all-in-UBI от другого инструмента, на сторонний образ и на нечитаемый зонд. Теперь они разведены:

- *Чем является плата* — из `/proc/device-tree/compatible`, первичного свидетельства, несущего и плату, и SoC, поэтому MD опознаётся по `airoha,an7581` даже без пригодного `board_name`. Суффикс `-ubi` сохраняет собственное узкое значение: происхождение, а не железо.
- *Что она выполняет* — классифицируется по разметке: `recovery`, `production`, `stock-layout`, `foreign-ubi`.
- *Что допускается дальше* — без изменений: только `recovery` и `production` сборки этого комплекта.

**Геометрия, описывающая операцию, и геометрия, которая её не описывает.** Полевое устройство опубликовало `mtd2=0x0FF00000` там, где сборка комплекта публикует `0x0FFE0000` — 7 eraseblock'ов, которые другая сборка оставляет неиспользованными, — и получило отказ. Но откат из работающей системы правит U-Boot environment, проверяет его обратным чтением, перезагружает устройство и отдаёт recovery-образ по TFTP в RAM; раздел `ubi` при этом не читается, не стирается и не пишется, а физическую цель recovery-система фиксирует сама до записи. Размер был отпечатком личности в одежде проверки безопасности. `/proc/mtd` теперь разбирается структурно: `all_flash` на 256 МиБ, `bl2` в `0x20000`, erase `0x20000` и имя `ubi`/`ibu` остаются точными, потому что заданы железом и загрузочным контрактом; размер раздела становится свидетельством `[RESTORE-SHAPE]` в логе сессии. Это правило RC25, применённое ещё на один путь: авторизовать по фактам, описывающим операцию, а остальное записывать.

**Fail-closed гейт обязан объясниться.** Зонд уже собрал имя платы и `/proc/mtd`; отказ не сообщал ни того, ни другого, оставляя оператора посреди инцидента гадать, какая половина не сошлась. Теперь отказ печатает наблюдаемое против ожидаемого, называет несовпавшую половину, перечисляет недостающие маркеры и указывает подходящий путь.

## 1.0.0-rc26 — разделение консоли и лога

**Контракт консоли, переформулированный.** RC23 поставил абсолютный таймстамп на операторские строки, чтобы вывод ПК можно было сопоставить с событиями UART; RC25 вывел из-под этого меню. RC26 доводит мысль до конца, задав вопрос, где сопоставление происходит на самом деле. Оно происходит в файле, который читают постфактум, — а не на экране, за которым работает оператор и где префикс в 21 символ отнимал место у сообщения в каждой строке. Поэтому консоль теперь показывает ровно то, что напечатал код, а `_ConsoleTee` штампует копию, уходящую в `work/logs/`. Время стоит у каждой строки лога, включая пункты меню и приглашения ввода, отчего лог стал лучшей записью, чем был.

Следствие: консольной машинерии подавления больше нечего подавлять. `menu_ui()`, `_MENU_RENDERING`, `_stamp_stream()` и `_timestamp_text()` удалены вместе со всеми двадцатью блоками `with menu_ui():`. Удаление проверено сравнением AST модуля до и после, так что исчезли только обёртки. Один инвариант заменил правило, которое приходилось заново применять к каждому новому селектору: консоль не штампуется никогда, лог — всегда, и разойтись они не могут без падения selftest'а.

Две детали держат лог честным. `_write_session_only()` пишет мимо tee и потому штампует себя сам, а `_log_prompt_newline()` сбрасывает позицию в логе, чтобы строка после приглашения начинала строку, а не продолжала её. Штамп по-прежнему префикс строки: кусок, продолжающий строку, проходит нетронутым — именно это оставляет живое зеркало UART читаемым и не даёт счётчику прогресса с `\r` собирать штамп на каждую перерисовку.

## 1.0.0-rc25 — symmetric write authorization / console and identity contracts

**Контракт разрешения на запись.** Карта stock-слотов `mtd2..mtd5` — это *классификатор*, а не allowlist. Она отвечает на вопрос «какое это семейство и какая vendor slot revision», и этот ответ питает только выбор backup и evidence. Разрешение на permanent write собирается из фактов, описывающих реальную цель записи: live family match, `/proc/mtd == sysfs`, точные фиксированные stock partitions, побайтно совпадающие stock handoff targets `mtd0/mtd14/mtd15/mtd16`, erase size `0x20000`, полный backup `mtd0..mtd16`, перепроверенный по содержимому, device-specific environment и pinned transition bundle. После перехода в RAM board-specific installer заново и независимо выводит физическую цель — `all_flash=0x10000000`, `BL2=0x20000`, `UBI/IBU=0x0FFE0000`, erase `0x20000`, write `0x800` — и только после этого `ubiformat` вообще достижим.

Следствие — симметрия: MD и MF теперь различаются профилем, геометрией и байтами payload, но не политикой. `MD_PERMANENT_WRITE_LAYOUTS`, `InstallProfile.allowed_stock_variant` и MF-only exact-гейт `MF-A` удалены, потому что vendor slot revision никогда не была свидетельством о физической цели, которую она разрешала. `BACKUP_HW_VALIDATED` понижен до evidence marker по той же причине: installer перечитывает и заново проверяет каждый выбранный backup вместо того, чтобы доверять токену.

Распознавание остаётся fail-closed там, где это уместно. Каноническая пара `00480000/02400000` обязана совпасть байт в байт; противоположный слот сверяется внутри окна, много уже половины расстояния между эталонными точками MD и MF, поэтому пара, попадающая в оба семейства, разрешается в `unknown`, а не в догадку.

**Контракт консоли.** RC23 установил, что операторские строки несут абсолютный таймстамп, чтобы вывод ПК можно было сопоставить с событиями UART. RC25 сужает это до того, ради чего оно вводилось, — до события. Текст селекторов (меню режима запуска, главное меню, все четыре подменю, ручной fallback выбора модели и запрос навигации после действия) выводится внутри `menu_ui()` — контекстного менеджера, который снимает префикс и всегда его возвращает, в том числе при исключении. Всё, что сообщает о событии, время сохраняет: операционный вывод, решения `[BLOCKED]`/`[SAFETY-LATCH]` и строки `[NAV]`, фиксирующие момент завершения действия. Инвариант держится структурно: случай в `selftest-safety` разбирает модуль и падает, если любая из этих функций спрашивает выбор или печатает нумерованный пункт вне блока `menu_ui()`.

**Контракт предупреждения.** Проверка LAN1 — первый в кодовой базе намеренно неавторитетный сигнал, и стоит объяснить, почему это не гейт. LAN1 — единственный порт 2.5G на обеих платах, поэтому линк, согласованный на 2500 Мбит/с и выше, опознаёт его положительно; но гигабитная сетевая карта ПК, воткнутая в LAN1, договаривается на 1000 и от LAN2..LAN4 неотличима. Детектор с такой долей ложноотрицательных срабатываний не может нести блокировку: он отвергал бы правильные подключения и всё равно пропускал бы ту самую ошибку, ради которой существует. Поэтому он предупреждает, по умолчанию продолжает, при нечитаемой скорости сводится к прежнему напоминанию о политике и сам по себе никогда не бросает исключение — единственный путь отказа — ответ оператора «нет». Selftest фиксирует эту форму, чтобы предупреждение не превратилось в гейт незаметно.

**Контракт «чтение по факту».** Классификация `mtd2..mtd5` — предусловие *записи*, но никогда не чтения. Установке семейство нужно, потому что этим выбором определяется прошивочный payload; backup в нём не нуждается. Read-only снятие авторизуется фиксированными stock-разделами, `/proc/mtd == sysfs`, размером erase `0x20000` и MAC, записанным в `DEVICE_MAC.txt`, — ничто из этого от ревизии слота не зависит. Поэтому `_stock_live_geometry_preflight()` принимает `require_slot_family`: снятие копии и диагностика передают `False` и работают с тем, что реально есть, сообщая нераспознанную разметку как evidence; `_install_live_gate()` сохраняет `True`. Отказ копировать NAND из-за сместившейся ревизии слота лишил бы образа для отката ровно того оператора, которому он и нужен, а смещение — штатное явление: поле уже дало `mtd4=0x003AF742` и `0x003AF61F` при эталоне `0x01CC0000`, отстоящем ровно на один eraseblock от края допуска. Расширять таблицу эталонов значит гнаться за каждой новой ревизией бесконечно; правильное решение — перестать завязывать на неё чтение.

Та же правка убирает два наследия более раннего релиза, где сверялись только с точной MD-таблицей: любой MF-backup, включая аппаратно подтверждённый точный MF-A, проваливался в отказ с утверждением, что установка MF ждёт отдельного HW gate. Это блокировало откат на сток без UART для MF. `verify_backup()` теперь пиннит наблюдаемые размеры слотов для обоих семейств, так что перекрёстная проверка dump/`proc` остаётся точной, а таблица семейств перестаёт быть гейтом.

**Пути по Reset.** На MD кнопка Reset ведёт в две разные точки входа в recovery, и решает момент нажатия относительно подачи питания. Нажатие Reset *после* подачи питания приводит в собственный Web recovery загрузчика tcboot: он уже инициализировал DDR, опознал SPI-NAND 256 MiB и поднял `eth0`/`httpd` — UART не нужен. Удержание Reset *до* подачи питания перехватывает управление раньше tcboot и приводит в BootROM с приглашением `Press x` — это и есть XMODEM-путь, который ведёт мастер. Это не варианты одной процедуры, и описывать их как одну нельзя. На MF сетевой слой tcboot не доказан — AN7583 требует своих PCS, MDIO, pinctrl и switch glue, — поэтому там следует рассчитывать только на путь через BootROM.

**Контракт идентичности.** Версия релиза объявлена в восьми местах: в коде, в JSON-метаданных, в текстовых файлах `VERSION` и в шаблоне launcher, потому что разные потребители читают разные из них. Дублирование значения, которое никогда не должно расходиться, безопасно только если расхождение обнаружимо, поэтому `selftest-safety` сверяет все восемь и падает на любом несовпадении. Он же отвергает суффикс `fix`: релизы в репозитории — цельные версии, а промежуточные `fix`-итерации складываются в тот релиз, к которому относятся. `verify_kit()` закрывает рантайм-половину той же идеи, сверяя `MANIFEST.release.version/build_tag/archive_root` с кодом, а шесть pinned payload — с записанными размерами и SHA256.

## 1.0.0-rc24 — interactive navigation / safety-latch contract

Интерактивный `wizard` теперь является persistent state machine, а не one-shot dispatcher. После каждого action обычный success/error завершается навигационным состоянием `section | main | exit`; исключение не завершает Python-процесс само по себе. Direct CLI subcommands остаются вне этого wrapper и сохраняют машинно-проверяемые exit codes.

Safety invariant: меню не является разрешением на destructive retry. `WriteStateUnknownError` устанавливает process-local `SAFETY-LATCH`; пока latch активен, normal install, no-UART restore и destructive Stage 2 недоступны. Разрешены read-only diagnostics/backup и полный BootROM/UART recovery. Только успешное завершение полного UART recovery снимает latch. `KeyboardInterrupt` не ловится interactive action wrapper'ом.

## 1.0.0-rc23 — timestamp/backup identity contract

Operator console contract: каждая непустая строка и prompt, проходящие через общий `master.py` print/input layer, получают абсолютный локальный prefix `[YYYY-MM-DD HH:MM:SS]`. Timestamp добавляется только к presentation layer и не меняет protocol markers, hashes, UART commands или NAND state-machine. Prompt завершается отдельным newline только в PC log, чтобы следующий timestamp не слипался с prompt; console не получает лишнюю пустую строку.

Backup identity contract: live-stock TFTP/USB backup создаёт `DEVICE_MAC.txt` до финального `SHA256SUMS`. Предпочтительный source — `/sys/class/net/eth0/address`; fallback — первый non-loopback sysfs interface. Файл содержит model/family, local+UTC capture time, primary interface/MAC и все найденные interface MACs. Если каталог resume уже привязан к другому известному MAC, TFTP backup fail-closed блокирует смешивание устройств. Отсутствие файла в legacy backup не является compatibility failure.

## 1.0.0-rc22 — bad-block-aware physical restore contract

UART stock restore теперь использует физическую модель canonical `mtd16`, а не logical compaction U-Boot `mtd write` через bad blocks. Контракт:

`RECOVERY_SAFE prompt -> exact geometry -> mtd bad bl2/ubi -> TFTP first chunk while NAND untouched -> explicit confirmation -> erase ubi -> rescan bad map -> physical good-span write/readback/CRC32 -> stable bad map -> BL2 LAST`.

Разрешённый автоматический skip внутри canonical stock span ограничен physical `0x052C0000..0x0EB60000`, где stock layout использует UBI-backed config/data/oopsfs/log_truncated. Для raw-critical областей BMT semantics не доказаны, поэтому bad block там является capability-gate failure. Ни один `mtd write` good-span не должен пересекать known bad eraseblock; RAM source offset всегда равен physical NAND offset относительно chunk, чтобы skip не сдвигал последующие данные.

**HW qualification (RC22/RC24):** exact bad-block restore остаётся не подтверждённым как полный stock restore. На реальном MF запись/readback завершились, stock main image/kernel загрузились, но `data` UBIFS не восстановился (`ubifs_recover_master_node`), после чего stock ушёл в watchdog reboot. Поэтому этот mapper нельзя считать HW PASS; до отдельного исправления/валидации его статус — partial hardware failure / recovery not validated.

## 1.0.0-rc19 — контракт restore transport

RC19 разделяет **ошибку транспорта до записи** и **неизвестное состояние NAND после старта записи**. До команды `mtd write` мастер может перейти `nokia-tftp -> TCP/nc -> SCP`. ## 1.0.0-rc18 — RECOVERY_SAFE RAM U-Boot / prompt capability gate

Banner U-Boot не считается доказательством контроля: обычный AN7581 RAM U-Boot имеет `bootdelay=0` и может выполнить first-boot `ubi_format -> mtd erase ubi` до доказанного интерактивного prompt. RC18 поставляет recovery-only SAFE derivatives FIP для AN7581/AN7583: BL31 сохраняется byte-for-byte, а BL33 получает `bootdelay=-1`, inert `bootcmd/preboot`, marker `medveflasher_recovery_safe=rc18` и нейтрализованные persistent UBI environment names, чтобы NAND `ubootenv/ubootenv2` не мог снова включить autoboot. После устойчивого prompt `master.py` требует exact SAFE marker, `bootdelay=-1`, inert bootcmd и свежий nonce, прежде чем появится NAND write/erase/saveenv capability; Ctrl-C после banner остаётся только вторичной страховкой, отправляемой paced-серией, а не один раз. Linux fallback после пропущенного prompt отключён fail-closed для обоих семейств, LAN1/2.5G по-прежнему запрещён для всех transition/recovery процессов, а full stock restore сохраняет прежний инвариант body/IBU erase+write+readback сначала, BL2 — LAST.

SAFE BL33 кодируется через `LZMA_FILTER_LZMA1EXT` (known size, no EOPM) в той же форме, что исходные Airoha payloads: первый опубликованный архив RC18 fail-closed останавливался до COM/XMODEM на строгой Windows liblzma с `Corrupt input data`, NAND при этом не затрагивалась. Runtime preflight больше не декодирует BL33 на ПК, а проверяет exact whole-FIP и compressed BL31/BL33 SHA256.

## 1.0.0-rc17fix5 — запрет LAN1/2.5G для transition/recovery

## RC16: provenance payload и build-time recovery transform

RC16 намеренно не пытается свести MD и MF к одному firmware build-set. Для MD production используется выбранный Dark patched snapshot 09.08.2026; для MF production остаётся Uname UBI set. BootROM recovery stages являются третьим, отдельным классом payload и не подменяются production bootloader-артефактами.

MD source initramfs Dark нельзя использовать как stock-recovery без изменения DT: production DT помечает `bl2` read-only и описывает `ubi`. RC16 сохраняет kernel/rootfs source image byte-for-byte, но пересобирает только recovery DT: `all_flash` read-only, `bl2` writable только в RAM recovery, `ibu` покрывает `0x20000..0x10000000`. Это build-time transform; runtime repack отсутствует. Он позволяет сохранить новые PHY/NPU/kernel изменения Dark и одновременно не нарушить доказанный порядок stock restore `IBU -> readback -> BL2 LAST -> readback`.

Release-integrity теперь связывает MANIFEST не только с SHA bundle, но и с фактическим FIT totalsize/FIT SHA и production size/SHA для MD auto/manual и MF auto/manual. Любой metadata drift fail-closed блокирует `verify_kit()`.

### RC10fix2: BootROM backup без SSH

Перед чтением NAND проверяются модель, `all_flash`, BusyBox applets и RAM-only TFTP probe. Каждый блок подтверждается вторым чтением NAND через SHA256. ## RC11: MF stock audit и разделение физической NAND/restore span

`STOCK_ALL_FLASH_SIZE` переименован в `STOCK_RESTORE_SPAN = 0x0EBA0000`. Это behavior-preserving изменение: все прежние операции backup/restore продолжают работать на том же диапазоне. Отдельная `PHYSICAL_NAND_SIZE = 0x10000000` служит только справочной геометрией известных AN7581/AN7583 устройств; stock audit не выводит ёмкость чипа из `mtd0`, потому что в штатной разметке `mtd0` — bootloader `0x00080000`. Фактическая физическая ёмкость берётся из NAND-driver/dmesg, а restore span — из `mtd16/all_flash` и сверяется с `/sys/class/mtd`.

Поддерживаются два реально встреченных MF-профиля и их зеркальные варианты:

```text
MF-A: mtd2=0x003B6CC0 mtd3=0x01D00000 mtd4=0x00480000 mtd5=0x02400000
MF-B: mtd2=0x003B6D40 mtd3=0x01D10000 mtd4=0x00480000 mtd5=0x02400000
```

Главное меню `credentials / stock audit` может выполнить строго диагностический путь: Web читает device-specific credentials, PC управляет интерактивным `su`, и `CAP_STOCK_ROOT=YES` появляется только после реального `id -u = 0`. Затем снимаются IDENTITY/USERS/SU/MTD/NAND-UBI/read-primitives/stock-upgrade inventory. Найденные upgrade-файлы не запускаются; write-verbs парсятся только из строк `AUDIT_HIT`, поэтому собственный grep-regex аудитора не может создать ложный hit.

Normal/permanent MF install в RC11 не включён. `CAP_FULL_BACKUP=READY FOR HW ENABLEMENT` означает только, что root/геометрия/read primitives согласованы для следующего аппаратного gate.

BootROM backup дополнительно защищён runtime firewall: каждая реально отправляемая RAM-shell команда перед UART TX проверяется на `mtd/nand write|erase`, `saveenv`, UBI destructive verbs, `sysupgrade` и `dd ... of=/dev/mtd*`.

При известной физической ёмкости `0x10000000` разница с restore span `0x0EBA0000` составляет `0x01460000` = **20.375 MiB**. RC11 не интерпретирует этот хвост как BMT автоматически: его назначение должно подтверждаться `dmesg`/vendor-механизмом.


## RC12/RC12fix: startup fingerprint и normal MF backup

После выбора языка мастер выполняет best-effort read-only fingerprint через stock Web (`ModelName`/chipset). Успешный результат помечается `VERIFIED`; ручной MD/MF fallback — только `UNVERIFIED` UI profile. Ни один backup/write backend не доверяет этому выбору: модель заново доказывается Web-данными и MTD geometry.

Normal MF backup использует отдельный additive backend, не переписывая подтверждённый MD install path. Gate: Web family MF → Telnet → `id -u == 0` → известный MF-A/MF-B slot layout → точные fixed partitions → `/proc/mtd == sysfs` → наличие `/dev/mtd0ro..mtd16ro`. Данные читаются только из `*ro` и передаются gzip/TFTP PUT. В rc12fix для `mtd16` один gzip-поток разветвляется `tee`: одна ветка идёт в TFTP, вторая — через FIFO в `sha256sum`; SHA256 router stream обязан совпасть с SHA256 принятого `.gz` на ПК. Повторное полное чтение live NAND не используется как gate, потому что mutable stock-разделы могут измениться между чтениями. Resume доверяет только локально целому gzip точного raw-размера с сохранённым transport-stream SHA256. Итоговый каталог принимает только `verify_stock_restore_backup()`.

`CAP_PERMANENT_INSTALL` для MF остаётся закрыт. Upgrade inventory rc12 расширяет read-only сбор metadata/strings/text, чтобы восстановить vendor upgrade semantics без запуска найденных utilities.


## RC13: прошивочные capability gates

Аппаратный rc12fix capture на MF-A закрыт end-to-end: Web → Telnet → `UID 0` → MF-A `/proc/sysfs` → `/dev/mtd*ro` → TFTP всех 17 MTD → SHA256 **того же gzip-потока** на Nokia и ПК → `verify_stock_restore_backup()` → `BACKUP_HW_VALIDATED`. Поэтому release-level статус normal MF-A backup повышен до `CAP_FULL_BACKUP=YES - HW CONFIRMED`. Для MF-B/зеркальных вариантов backend остаётся live-gated, но собственный end-to-end аппаратный capture ещё нужен для статуса HW CONFIRMED.

rc13 вводит два слоя capability-оценки. `data/FIRMWARE_CAPABILITIES.json` хранит release-level hardware evidence, а `firmware_capabilities_wizard()` пересекает его с текущими read-only фактами устройства: Web family, Telnet, `id -u == 0`, известный slot variant и `/proc/mtd == sysfs`. Capability report не является разрешением на запись: destructive функции сохраняют собственные fail-closed preflight и подтверждения.

Для MF write-capabilities намеренно разделены:

```text
CAP_RAM_OPENWRT          PARTIAL
CAP_UBI_FORMAT           BLOCKED
CAP_UBI_VOLUME_WRITE     BLOCKED
CAP_BOOTLOADER_REPLACE   BLOCKED
CAP_PERMANENT_INSTALL    BLOCKED

```

`PARTIAL` для `CAP_RAM_OPENWRT` означает: BootROM/RAM recovery доказан, но normal-install transition как часть permanent MF install ещё не является подтверждённым write-path gate. rc13 не добавляет ни `ubiformat`, ни `ubi write`, ни замену bootloader для MF. Если startup Web уже подтвердил MF, MD-only install entries блокируются в UI до входа в старый MD wizard; это дополнительный guard, не замена внутренних MD model/backup checks.


## rc14: отдельный MF-A transition-to-RAM write gate

rc14 не переиспользует MD installer как универсальный backend. Для MF добавлены отдельные `MF_TRANSITION_BUNDLE`, `MF_TRANSITION_LAUNCHER_TEMPLATE`, `personalize_mf_transition()` и `mf_transition_to_ram_wizard()`. Это сохраняет подтверждённый MD путь неизменным.

MF-A gate требует одновременно: startup/profile `VERIFIED MF`, повторный live Web fingerprint MF, Telnet → доказанный UID 0, `/proc/mtd == sysfs`, variant `MF-A`, полный `verify_stock_restore_backup()` и marker `BACKUP_HW_VALIDATED` с `family=mf/variant=MF-A`. MF-B и зеркальные варианты только распознаются и fail-closed блокируются.

Пакет привязан к текущему исходному erase-block U-Boot environment. Launcher снова проверяет текущий SHA исходного `mtd0+0x60000` перед erase. Порядок записи: `mtd14/nsb_master` erase/write → полный readback SHA256 → повторный source-env SHA → `mtd0` erase `0x60000/0x20000` → write персонального erase-block → readback SHA256 → reboot. `bootflag`, `bosa`, `ri`, `data`, UBI metadata и bootloader body не меняются.

После reboot PC ждёт исчезновение stock services и доказывает RAM OpenWrt через LuCI redirect/content либо SSH identity `xg-040g-mf`/`AN7583`. При успехе создаётся `MF_TRANSITION_HW_VALIDATED.json`. При сетевой неопределённости workflow падает с требованием UART-лога; никакой stage2 не запускается автоматически. `CAP_UBI_FORMAT`, `CAP_UBI_VOLUME_WRITE`, `CAP_PERMANENT_INSTALL` остаются отдельными закрытыми gates.

## rc14fix: permanent MF-A all-in-UBI path

MF-A использует ту же двухфазную модель, что и MD. Stock-side launcher не форматирует UBI: он повторно подтверждает MF-A, bundle/env SHA256 и stock boot path, переносит минимальный worker в RAM, пишет выбранный auto/manual bundle в `mtd14` и проверяет полный readback, затем повторно сверяет исходную environment и пишет только erase-block `mtd0` `0x60000..0x7ffff` последним.

После reboot transition initramfs идентифицирует `nokia,xg-040g-mf-ubi`, проверяет физический NAND `all_flash=0x10000000`, `bl2=0x20000`, `ubi=0x0ffe0000`, pinned preloader/FIP и sysupgrade. До `ubiformat` из stock physical view сохраняются `bosa` (`0x51c0000+0x40000`), `ri` (`0x5200000+0x40000`) и текущий transition FIT (`0x0c0000`). Затем создаются фиксированные UBI volume IDs: 0 `ubootenv`, 1 `ubootenv2`, 2 `bosa`, 3 `ri`, 4 `fip` static 1 MiB, 5 `fit`. bosa/ri/FIP/fallback FIT проверяются чтением и SHA256. Полный 128-KiB BL2 container (FF prefix `0x800`, preloader с offset `0x800`) записывается **последним** и проверяется чтением. После этого auto mode запускает bundled `sysupgrade`; manual mode принимает выбранный ПК-образ только после `sysupgrade -T` и SHA256 gate.

Этот permanent path в rc14fix включён только для MF-A и помечен experimental до первого успешного end-to-end прогона. UART/BootROM full stock restore уже hardware-confirmed и является rollback.


## rc14fix2: RAM-worker и operator-clean UI

MF stage 1 сохраняет прежнюю архитектуру и destructive gates. Изменён только runtime bootstrap: staged BusyBox запускает `flash.sh` через applet `sh`, потому что реальный stock BusyBox MF не объявляет отдельный `ash` applet. Подробный preflight не выводится оператору; raw transcript хранится в timestamped session log, а `LATEST.log` отражает только пользовательский поток.

## rc14fix3: единый MD/MF installer engine

Установка больше не имеет отдельной MF orchestration-ветки. `InstallProfile` задаёт family/model, auto/manual bundle, runtime-имена, expected UBI board и variant/backup policy. Общий `install_openwrt_wizard(profile, from_existing_backup)` выполняет backup/deploy/stage1/stage2, а `personalize_transition(profile, ...)` использует один `stock-launcher.sh.in`. MF-A сохраняет дополнительные fail-closed gates. Готовые transition bundles не пересобираются при запуске. Standalone MF transition FIT/sysupgrade и production preloader/FIP не входят в runtime kit, поскольку их байты уже находятся внутри соответствующих bundles/initramfs.


## rc14fix4: отказоустойчивый UART mirror

На stock MF `/dev/console` не является надёжным диагностическим sink: наличие character-device и write bit не гарантирует успешную запись. В rc14fix3 UART был одним из прямых outputs `tee`, поэтому `EIO` на `/dev/console` мог разрушить общий FIFO/log pipeline до запуска RAM-worker.

В rc14fix4 основной `tee` отвечает только за caller/session/USB logs. Опциональный UART получает копию через отдельный FIFO, который всегда вычитывает relay-процесс. При первой ошибке UART relay прекращает serial writes, но продолжает drain FIFO, поэтому primary `tee`, RAM-worker и destructive state machine не зависят от serial device. `/dev/ttyS0` имеет приоритет над `/dev/console`. Safety gates и NAND write ordering не изменены.


## rc14fix6: прямой probe RAM BusyBox applet

Pre-write self-test больше не считает вывод `busybox` без аргументов переносимым реестром applet. Vendor BusyBox может не печатать секцию `Currently defined functions`, поэтому такой парсинг давал ложный `missing` на первом проверяемом имени. Общий MD/MF launcher теперь сначала доказывает `echo` и `sh`, затем для каждого реально требуемого RAM applet запускает `busybox <applet> --help` со stdin=`/dev/null` и трактует только явное `applet not found` как отсутствие. Этот блок выполняется до erase/write; destructive state machine и BL2-last не менялись.


## rc15: transition-only writable BL2 и live stage2 monitor

MF production DT сохраняет `bl2` read-only как software safety barrier. Только auto/manual transition FIT содержит DT без `read-only` на разделе `bl2` и с marker `medveflasher,transition-writable-bl2`. Installer до UBI format требует marker и `MTD_WRITEABLE`; после UBI readback и непосредственно перед BL2-last повторно доказывает pinned preloader/FIP/complete-BL2 provenance. Общий MD/MF `run_stage2` получает state/log через deterministic BatchMode SSH, а при недоступности SSH — через read-only Telnet fallback. Канал мониторинга не авторизует destructive actions.


## RC17 control-plane invariant

Transition определяется по содержимому (`MEDVEFLASHER_TRANSITION_PROTOCOL=1`), а не по факту открытия TCP-порта. On-device shell protocol/log файлы только ASCII. Power-cycle можно предлагать только после ранее подтверждённого pre-destructive состояния с `SAFE_TO_POWER_CYCLE=1`; после `[1/8]` или `FORMATTING_AND_FLASHING` отключение питания никогда не рекомендуется. Гейты Restore Stock привязаны к family валидированного backup (MD/MF).
## RC17fix: post-restore boot proof

Успех записи NAND и успех последующей загрузки — разные состояния. UART restore сначала завершает все readback-проверки, затем отдельно подтверждает выполнение U-Boot `reset`. Stock boot считается успешным только после content fingerprint штатной Nokia login page; TCP connect сам по себе является только transport telemetry. При неподтверждённом reset оператору разрешается один power-cycle только после завершённого BL2 readback.


### RC20: pre-destructive Telnet re-arm

После операторского подтверждения старый stock Telnet-сеанс не считается живым по умолчанию. Мастер делает nonce-probe, при необходимости переподключается, повторяет read-only preflight и только затем один раз отправляет `--flash`. Любая потеря канала после попытки dispatch переводит состояние в `STAGE1_HANDOFF_UNKNOWN`; destructive retry запрещён. TFTP является первым рекомендуемым transport path во всех операторских меню.
